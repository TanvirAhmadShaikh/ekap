Technical Documentation

Full-stack architecture reference for the Enterprise Knowledge Assistant Platform (EKAP).

Overview

EKAP is a fully self-hosted, open-source enterprise knowledge assistant. Employees query company knowledge in natural language and get answers grounded in permitted documents, with citations. There are no external AI services or proprietary software dependencies — every component runs on infrastructure the organization controls.

Core design principles: centralized storage (no client-side document copies), security-first (permission checks always run before retrieval), and zero-trust between internal services.

Architecture Flow

Users → NGINX → Employee Portal (chat panel) → FastAPI Gateway (retrieval-service)
                              → Retrieval Router
                                  → Vector (Qdrant)
                                  → Hierarchical (Doc→Chapter→Section→Chunk)
                                  → BM25
                                  → Metadata filter
                              → Context Builder → vLLM → Response (with citations)

The Admin Portal and Employee Portal are separate static SPAs served by NGINX alongside the proxied services; they call ingestion-service and retrieval-service directly over /api/* and /v1/chat/completions.

Services (Docker Compose)

Defined in docker-compose.yml, on the shared ekap-net network:

  • nginx — single entrypoint, TLS termination, routing, static hosting for admin-ui and employee-portal.
  • keycloak + keycloak-setup — identity provider; the setup container bootstraps the ekap realm and ekap-web client on first run.
  • postgres — metadata DB backing both the app and Keycloak's own store.
  • qdrant — vector index for embeddings.
  • vllm — GPU-backed OpenAI-compatible LLM inference server.
  • retrieval-service — FastAPI; query orchestration, security enforcement, chat/completions.
  • ingestion-service — FastAPI; upload, extraction, classification, chunking, embedding, indexing, folders/workflow.
  • prometheus + grafana — metrics collection and dashboards.

Ingestion Pipeline

Upload → Virus Scan → Text Extraction → Metadata Extraction
       → Classification → Chunking → Embedding Generation
       → Index Creation → Storage

Supported formats: PDF, DOCX, TXT, Markdown, HTML, CSV, Excel, PowerPoint, Confluence exports, Wiki pages.

Document classification fields

document_id, title, owner, department, creation_date, last_modified_date, version, classification_level (Public/Internal/Confidential/Restricted), tags.

Documents flow through a workflow state machine (Draft → In Review → Approved → Published → Archived/Trash) managed by ingestion-service and surfaced in the Admin Portal's Approval Queue.

Retrieval Strategy

Strategy is chosen by document size:

  • Small docs (<50 pages) — vector retrieval (Qdrant).
  • Medium docs (50–300 pages) — hierarchical retrieval (Doc → Chapter → Section → Chunk).
  • Large docs (>300 pages) — document-level retrieval with long context processing.
  • Hybrid — combines vector + BM25 + hierarchical signals, ranks, and selects the highest-confidence result.

Every answer returned to a user must include citations: Document Name, Section Name, Page Number, Confidence Score, and a Source Link.

Security / RBAC

Roles: User, Power User, Administrator, Knowledge Manager, System Administrator. Roles and group membership live in Keycloak.

The permission check runs before retrieval on every query — unauthorized chunks are filtered out before they ever reach the context builder, so a user can never see content their role/classification doesn't permit, even indirectly through a generated answer.

Both retrieval-service and ingestion-service validate bearer tokens against Keycloak (KEYCLOAK_URL / KEYCLOAK_REALM); see auth.py in each service.

Single entrypoint on port 80 (nginx/nginx.conf):

Rate limiting zones: api (60 req/min per IP) and upload (10 req/min per IP, stricter due to upload cost).

Deployment

Development: docker-compose.yml brings up the full stack locally.

Production: Kubernetes manifests under k8s/, applied via kustomization.yaml:

  • 00-namespace.yaml, 01-secrets.yaml
  • 02-storage.yaml — persistent volumes
  • 03-data-layer.yaml — Postgres, Qdrant
  • 04-keycloak.yaml
  • 05-app-services.yaml — retrieval-service, ingestion-service
  • 07-monitoring.yaml — Prometheus, Grafana
  • 08-ingress.yaml

Observability & Backups

Prometheus scrapes service metrics (prometheus/prometheus.yml); Grafana visualizes them, reachable via the Admin Portal's external link.

Backup/restore scripts live in scripts/ (backup.sh, restore.sh); bundle.sh packages a release bundle. Daily backups are required, target RTO <4h.

Non-Functional Requirements

  • Availability: 99.5%
  • Concurrency: 500+ simultaneous users
  • Response target: <10s typical, 60s hard timeout
  • Zero-trust internal architecture — services authenticate to each other, not just the edge
  • Daily backups, RTO <4h
